* Why dogfood

The first version of this document tried to write the dogfood as a
clever trick — sakshi-the-tool validating sakshi-the-codebase as if it
were a pipeline. That framing was wrong. sakshi /is/ a pipeline in the
relevant sense: org files are inputs, tangled Python files are
derived-from-measurement outputs, the test suite is the validation
step, and the published package is the final artefact.

The doctrine applies. The manifest is honest.

Dogfooding here means two things:

1. *sakshi's build is described by a sakshi manifest*, committed at
   the repository root as ~sakshi.manifest.yaml~. The manifest is
   discovered by sakshi's own pytest plugin and validated like any
   other manifest. If sakshi cannot describe its own build cleanly
   under its own discipline, the discipline is incoherent.

2. *The test suite includes a test that asserts the manifest's
   register coherence against the actual build artefacts*. This is the
   minimum amount of /coupling/ — between manifest declarations and
   actual on-disk state — that v0.1 ships. It is small. It is the
   point.

* The build pipeline, in doctrine terms

| Input artefact | Register | Operation | Output artefact | Output register |
|----------------+----------+-----------+-----------------+-----------------|
| codev/*.org | measurement | org-babel tangle | src/sakshi/*.py | derived-from-measurement |
| codev/*.org | measurement | org-babel tangle | test/test_*.py | derived-from-measurement |
| src + test | derived-from-measurement | pytest run | (test pass/fail) | derived-from-measurement |

The org files are the /source of truth/ — the cardinal rule in
CLAUDE.md and system.md says so. In sakshi's vocabulary that makes
them ~measurement~: they are the original recorded statement that
everything downstream is derived from. The tangled Python files are
~derived-from-measurement~ via the named derivation
~org-babel-tangle~. The test suite is itself a
~derived-from-measurement~ artefact (it was tangled the same way).

There is no synthetic-acknowledged register anywhere in sakshi's own
build. v0.1 was authored with LLM assistance, and the
~llm_assistance~ field of the manifest records that — but the LLM
produced the org content, which is now the measurement. The
distinction is the same one the doctrine makes for human-written code:
the author is recorded, the register of the artefact depends on what
the artefact is and what was done to it, not on who wrote it.

* The test file

#+begin_src python :tangle ../test/test_dogfood.py
"""sakshi validates its own build pipeline.

This file is tangled from codev/dogfood.org.

Four assertions:

1. The manifest loads under sakshi's own schema.
2. All declared inputs exist on disk.
3. All declared outputs exist on disk.
4. No silent extras — src/sakshi/ has no .py files beyond manifest outputs.

The third and fourth tests together enforce the cardinal rule that the
source-of-truth is codev/*.org. If a .py file exists without a
corresponding org source, it is a silent demotion of the discipline.
"""

from __future__ import annotations

from pathlib import Path

import pytest

from sakshi import Manifest, load_manifest

REPO_ROOT = Path(__file__).resolve().parent.parent
MANIFEST_PATH = REPO_ROOT / "sakshi.manifest.yaml"


@pytest.fixture(scope="module")
def manifest() -> Manifest:
    return load_manifest(MANIFEST_PATH)


def test_manifest_loads(manifest: Manifest):
    """sakshi must be able to describe its own build under its own schema."""
    assert manifest.step == "sakshi-build-v0.1"
    assert manifest.mode.value == "reconstruction-and-simulation"
    assert len(manifest.inputs) > 0
    assert len(manifest.outputs) > 0


def test_all_inputs_exist(manifest: Manifest):
    """Every declared input must exist on disk."""
    missing = []
    for inp in manifest.inputs:
        path = REPO_ROOT / inp.id
        if not path.exists():
            missing.append(inp.id)
    assert not missing, (
        f"Manifest declares inputs that do not exist on disk: {missing}. "
        "Either the inputs were deleted (revert) or the manifest is stale "
        "(update)."
    )


def test_all_outputs_exist(manifest: Manifest):
    """Every declared output must exist on disk after tangle."""
    missing = []
    for out in manifest.outputs:
        path = REPO_ROOT / out.id
        if not path.exists():
            missing.append(out.id)
    assert not missing, (
        f"Manifest declares outputs that do not exist on disk: {missing}. "
        "Run `make tangle` (or org-babel-tangle-all in Emacs)."
    )


def test_no_silent_extras(manifest: Manifest):
    """src/sakshi/ must contain only files declared in the manifest.

    A .py file in src/sakshi/ without an org source is a silent demotion
    of the source-of-truth rule.
    """
    declared = {
        out.id
        for out in manifest.outputs
        if out.id.startswith("src/sakshi/")
    }
    actual_py = {
        f"src/sakshi/{p.name}"
        for p in (REPO_ROOT / "src" / "sakshi").glob("*.py")
    }
    # Ignore __pycache__ etc., which glob does not return.
    extras = actual_py - declared
    assert not extras, (
        f"Found src/sakshi/ .py files not declared in the manifest: "
        f"{extras}. Either back-port them to codev/*.org and re-tangle, "
        f"or remove them."
    )
#+end_src

* What dogfood does and does not prove

It does prove:

- The schema is expressive enough to describe a real (small) build
  pipeline.
- The pytest plugin can discover and run a manifest from the
  repository root.
- The cardinal rule (org is source-of-truth) has a structural enforcer
  beyond the CLAUDE.md note.

It does not prove:

- That the doctrine is right. The doctrine's correctness is argued in
  ~codev/doctrine.org~ and demonstrated in the synthetic and IMIS
  examples; the dogfood is consistency-with-doctrine, not
  validation-of-doctrine.
- That sakshi's build is bug-free. The four assertions catch a narrow
  class of drift between manifest and on-disk state.

The dogfood is, in the doctrine's own vocabulary, a *coherence check*
on the discipline, not a proof of it.
