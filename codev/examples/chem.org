* Epistemic status — read this first

This example is a *portability sketch*, not a credibility-anchored
demonstrator. Three things to understand before reading further:

1. *No chem-practitioner has reviewed this file.* The descriptor
   pipeline calls real RDKit primitives, the SMILES are real public
   compounds, and the Lipinski Ro5 formula is textbook. But the
   /assembly/ of those pieces into a "chemoinformatics workflow"
   has not been validated by anyone who actually does medicinal
   chemistry or chemoinformatics for a living. The templated
   "SAR insight" string in particular is a stub, not chemistry —
   no medicinal chemist would write or read that string in a real
   workflow.

2. *The claim this example makes is narrow.* It claims: *sakshi's
   schema accommodates a molecule-as-graph topology — distinct
   from both sensor-point time series (IMIS) and raster stacks
   (the v0.2 InSAR demonstrator) — without modification, using
   only sakshi's generic vocabulary (register, derivation,
   synthesis, mode).* That claim is structurally testable from the
   manifest alone and is asserted in
   ~test_chem_manifest_uses_no_chemistry_specific_schema_fields~.

3. *The claim this example does NOT make.* It does not claim that
   sakshi's discipline is /sufficient/ for chemoinformatics
   pipelines, nor that the workflow assembled here is what a
   Roche/CADD/medchem reviewer would consider a faithful
   chemoinformatics workflow. A real chemoinformatics
   demonstrator would need: a chem-practitioner reviewer, a
   realistic dataset (not eight hand-picked textbook compounds),
   and a synthesis layer that is /either/ an actual LLM call /or/ a
   substantive descriptor-based prediction (not a templated
   string). v0.1 has none of these.

This sketch sits at the same epistemic tier as ~synthetic.org~ —
both are pedagogical illustrations of the discipline. The
credibility-anchored demonstrator in v0.1 is ~imis.org~, which
has WSL behind the substrate and parbati behind the reviewer
pipeline. v0.2 will either find a chem-practitioner reviewer
(re-tiering this file to demonstrator) or retire the sketch.

This honest framing is itself a sakshi-discipline move: refusing
to silently promote a portability sketch into a demonstrator's
epistemic register is exactly the kind of register-honesty
sakshi's firewall is designed to enforce.

** Bend-or-hold record: what did and did not strain when chem was assembled

The narrow claim "sakshi's schema accommodates a molecule-as-graph
topology without modification" is the kind of claim that is easy to
make by *silence* — by the absence of any schema edit. Silence is
not evidence. This subsection makes the bend-or-hold record
explicit, so a reader can falsify it rather than infer it.

*** What did NOT need to be added

- No new ~Register~ enum value. The four-register firewall
  (~measurement~, ~derived-from-measurement~, ~synthetic-acknowledged~,
  ~expression-mode~) carried the chem pipeline unchanged. SMILES is
  measurement, descriptors and Lipinski violations are
  derived-from-measurement, the templated SAR insight is
  synthetic-acknowledged. No fifth register surfaced.
- No new ~Mode~ enum value. ~reconstruction-and-simulation~
  accommodated the workflow; ~expression~ was not needed because
  the chem example is not a rendering for human-perception
  consumption (no figure-rendering step).
- No new ~Output~ field. ~derivation~ named "rdkit-descriptor-suite-v2024"
  and "lipinski-ro5-violation-count" cleanly; ~synthesis~ named
  "templated-sar-insight-stub" cleanly. The existing
  ~re_measurement~ field was not needed (no expression-mode inputs).
- No new ~Input~ field. The SMILES dataset is a single
  measurement-tagged input; no new metadata required.
- No new validator. The existing ~Manifest._check_doctrine~
  validators caught the two broken-by-construction chem manifests
  with their existing B-class raises (missing-derivation,
  missing-synthesis).
- No widening of the ~LlmAssistance~ vocabulary. The chem clean
  manifest uses ~level: none~ (the templated stub is not LLM-
  authored code); the IMIS-style gap-fill manifest pattern with
  ~level: pair-programmed~ would carry to a future chem manifest
  without change.

*** What DID strain (held under strain, but worth naming)

- *The compound register tag carried the load.* In the chem
  pipeline as built, no single output needed a compound register
  (each output is either ~derived-from-measurement~ or
  ~synthetic-acknowledged~, not both). But the design space tested
  the compound tag: had the SAR-insight layer been written to
  output a dataframe with /both/ deterministic descriptors and
  templated insights in one artefact, the compound tag
  ~[derived-from-measurement, synthetic-acknowledged]~ would have
  been required, and the schema would have demanded /both/
  ~derivation~ /and/ ~synthesis~ fields. The fact that this works
  out-of-the-box is a non-trivial design property of the v0.1
  schema. Worth naming as "tested in design, held".
- *The synthesis-field naming convention strained against the
  templated-stub-vs-LLM distinction.* In v0.1, the ~synthesis~
  field is a free-form string. The clean chem manifest names it
  "templated-sar-insight-stub". If the implementation were swapped
  to an actual LLM call, the natural ~synthesis~ value becomes
  something like "claude-opus-4-6-medchem-prompt-v3" — but the
  /register/ stays ~synthetic-acknowledged~. The schema does not
  enforce any structure on the synthesis field's value, only its
  presence. This is the right call for v0.1 (don't over-fit), but
  it is worth noting that a v0.2 reviewer might want richer
  synthesis-provenance (model id, prompt hash, temperature, etc.).
  That is a candidate v0.2 enrichment, not a v0.1 finding.

*** What would NEED to bend if chem were re-tiered to demonstrator

This is forward-looking — the actual schema-design discussion
belongs in v0.2-thinking-time, not here, but naming the likely
bend points so they are not surprises:

- A ~substrate_reviewer_id~ field (or equivalent) would likely
  need to be added to ~Manifest~, so the absence of a chem-
  practitioner reviewer is *recorded* rather than implicit. This
  is dhara@parbati's proposal raised in the v0.1 review of this
  file; banked into ~codev/v0.2-candidates.org~ as a candidate,
  not a commitment.
- A richer synthesis-provenance structure (see above) may be
  needed if the templated stub is replaced with an actual LLM
  call and the schema needs to capture reproducibility metadata.
- No other bend points have surfaced.

*** Honest summary

The portability-sketch claim held. No schema field, register
enum, mode enum, or validator needed modification to accommodate
the chem pipeline as built. The compound register tag was tested
in design (would have worked) but not used in the final
implementation. The synthesis field's free-form string
convention held but may need enrichment if chem is later re-
tiered to demonstrator.

The schema-validity question — "is what sakshi captures
*correct* for chemoinformatics?" — is mayadev's domain and
remains open. The substrate-validity question — "is this a
real chemoinformatics pattern?" — is the chem-practitioner's
domain and remains open. The bend-or-hold record above
addresses neither; it addresses only schema-accommodation.

* Purpose

This file is the literate source of the chemoinformatics portability
sketch. It ships:

- A *small synthetic SMILES dataset* — eight Lipinski-friendly drug-like
  scaffolds drawn from public textbook chemistry (aspirin, ibuprofen,
  caffeine, paracetamol, and four small Bemis–Murcko cores). The
  dataset is hand-curated and bundled into the repository so the
  example runs anywhere without external data fetches.
- A *deterministic descriptor pipeline*: SMILES → RDKit descriptors
  (molecular weight, LogP, TPSA, hydrogen-bond donors/acceptors) →
  Lipinski Rule-of-Five violation count.
- A *templated synthetic-prediction layer* — a deterministic-but-
  string-templated function that takes the descriptors and emits a
  "SAR-style insight" string. This is the layer that *would be* an
  LLM call in a real drug-discovery workflow; we substitute a
  templated string so the example is reproducible and license-clean,
  while keeping the register honest (~synthetic-acknowledged~).
- Three manifests demonstrating a typical chemoinformatics workflow.
  One is doctrinally correct; two are deliberately broken in ways
  that catch the LLM-induced sins the firewall is designed to
  prevent.
- A pytest test file that exercises the workflow end-to-end and
  asserts that the broken manifests fail with the expected B-class
  messages.

** Why a chemoinformatics sketch, when sakshi was built for environmental data?

sakshi's doctrine is /designed/ to be a property of scientific data
pipelines under LLM pressure, not of any single domain. The
four-register firewall and the two-mode polymorphism are intended
to apply whenever:

1. There is a measurement substrate (here: a SMILES string is a
   measurement of an actual chemical compound).
2. There are derived quantities (here: descriptors like LogP, TPSA,
   computed deterministically from the measurement).
3. There is an LLM-or-synthetic layer that produces plausible-looking
   outputs not anchored to the measurement (here: the
   "SAR-style insight" string).

This portability sketch exists to make that design intent /testable
from the manifest structure alone/. If sakshi only ever illustrates
itself on its native substrate (environmental-sensor time series), a
reader might fairly ask whether the doctrine is substrate-neutral or
just substrate-hidden. The sketch makes the question concrete: the
chem manifest uses only sakshi's generic vocabulary (register,
derivation, synthesis, mode), and the
~test_chem_manifest_uses_no_chemistry_specific_schema_fields~ test
makes that claim falsifiable. /Nothing in sakshi's schema or firewall
mentions chemistry./

What this sketch does *not* establish: that sakshi's discipline is
sufficient for actual chemoinformatics practice. That would require
a chem-practitioner reviewer, which v0.1 does not have. See the
"Epistemic status" section above.

** What this example does NOT do

- It does not call RDKit's full machine-learning stack. The
  descriptors are deterministic, license-clean, and identical across
  RDKit versions for the small bundled scaffolds.
- It does not call an LLM. The "SAR-style insight" layer is a
  templated string built from the descriptors. The discipline being
  demonstrated is independent of whether an LLM is actually invoked
  — the register is what matters.
- It does not claim domain expertise. The descriptor choices and the
  Lipinski Ro5 framing are textbook chemoinformatics; the worked
  example demonstrates sakshi's discipline applied to a faithfully-
  shaped chemistry pipeline, not novel medicinal-chemistry insight.

"""Hand-curated small SMILES dataset for sakshi's chemoinformatics example.

This file is tangled from codev/examples/chem.org.

Each entry is a public, textbook drug-like compound or a small

Columns when written to CSV:
    compound_id  -- short identifier

from __future__ import annotations

SMILES_SEED = [
    # Drug-like reference compounds (public textbook chemistry).
    ("ASP", "aspirin",     "CC(=O)Oc1ccccc1C(=O)O"),
    ("IBU", "ibuprofen",   "CC(C)Cc1ccc(C(C)C(=O)O)cc1"),
    ("CAF", "caffeine",    "Cn1cnc2c1c(=O)n(C)c(=O)n2C"),

    # Small Bemis–Murcko-style scaffolds for descriptor variety.
    ("PYR", "pyridine",    "c1ccncc1"),
    ("IND", "indole",      "c1ccc2[nH]ccc2c1"),
    ("QIN", "quinoline",   "c1ccc2ncccc2c1"),
    ("THI", "thiazole",    "c1cscn1"),

    """Write the seed dataset to a CSV at out_path."""

* The descriptor and Lipinski layers

This is the deterministic, RDKit-backed derivation layer. Given a
SMILES string, RDKit emits a fixed set of physico-chemical descriptors
(molecular weight, LogP, TPSA, HBD count, HBA count). Lipinski Rule-of-
Five violation count is then computed from those descriptors by a
textbook formula.

The register of these outputs is ~derived-from-measurement~. The
~derivation~ field names the procedure ("rdkit-descriptor-suite-v2024"
and "lipinski-ro5-violation-count").

If RDKit is not installed, the test file skips the workflow tests; the
manifest-level tests run regardless.

#+begin_src python :tangle ../../test/chem/descriptors.py
"""Deterministic descriptor and Lipinski-Ro5 layer for the chem example.

This file is tangled from codev/examples/chem.org.

Optional dependency: RDKit (install with `pip install sakshi[chem]`).
If RDKit is not available, descriptor functions raise ImportError and
the test runner skips the workflow tests.
"""

from __future__ import annotations

from dataclasses import dataclass

try:
    from rdkit import Chem
    from rdkit.Chem import Crippen, Descriptors, Lipinski

    RDKIT_AVAILABLE = True
except ImportError:  # pragma: no cover
    RDKIT_AVAILABLE = False


@dataclass(frozen=True)
class MolDescriptors:
    """The fixed descriptor suite produced by rdkit-descriptor-suite-v2024."""

    compound_id: str
    molecular_weight: float
    logp: float
    tpsa: float
    hbd_count: int
    hba_count: int


def compute_descriptors(compound_id: str, smiles: str) -> MolDescriptors:
    """Compute the descriptor suite for a single SMILES.

    Procedure name: rdkit-descriptor-suite-v2024
    """
    if not RDKIT_AVAILABLE:
        raise ImportError(
            "RDKit not installed. Install with `pip install sakshi[chem]`."
        )
    mol = Chem.MolFromSmiles(smiles)
    if mol is None:
        raise ValueError(f"RDKit could not parse SMILES for {compound_id!r}: {smiles!r}")
    return MolDescriptors(
        compound_id=compound_id,
        molecular_weight=round(Descriptors.MolWt(mol), 2),
        logp=round(Crippen.MolLogP(mol), 2),
        tpsa=round(Descriptors.TPSA(mol), 2),
        hbd_count=Lipinski.NumHDonors(mol),
        hba_count=Lipinski.NumHAcceptors(mol),
    )


def lipinski_violations(d: MolDescriptors) -> int:
    """Count the number of Lipinski Rule-of-Five violations.

    Procedure name: lipinski-ro5-violation-count

    Ro5 (Lipinski 1997): a drug-like molecule typically has
        MW <= 500, LogP <= 5, HBD <= 5, HBA <= 10.
    """
    violations = 0
    if d.molecular_weight > 500:
        violations += 1
    if d.logp > 5:
        violations += 1
    if d.hbd_count > 5:
        violations += 1
    if d.hba_count > 10:
        violations += 1
    return violations
#+end_src

* The templated synthetic-prediction layer

This is the layer that would be an LLM call in a real workflow. We
substitute a deterministic templated string so the example is
reproducible and license-clean.

Crucially, the register stays honest: the output is
~synthetic-acknowledged~, with a ~synthesis~ field naming the procedure
("templated-sar-insight-stub" — replaced in production by an actual
LLM-call procedure name like "claude-opus-4-6-medchem-prompt-v3").

The point of this layer is *not* that the templated string is useful
chemistry — it isn't. The point is that the discipline treats this
class of output identically whether the generator is a templated
string or a state-of-the-art chemistry LLM. The register is the
honest answer to "where did this come from?"

#+begin_src python :tangle ../../test/chem/insight.py
"""Templated synthetic-prediction layer for the chem example.

This file is tangled from codev/examples/chem.org.

The function in this file would, in a production drug-discovery
workflow, be a call to an LLM (Claude, GPT-4, a medchem-fine-tuned
model). We substitute a deterministic templated string so:

1. The example runs anywhere without API keys.
2. The output is bit-identical across runs.
3. The discipline being demonstrated does not depend on the actual
   text content — it depends on the *register*.

The register is ~synthetic-acknowledged~, and the manifest's
~synthesis~ field names the procedure honestly.
"""

from __future__ import annotations

from .descriptors import MolDescriptors


def sar_insight_stub(d: MolDescriptors) -> str:
    """Emit a templated SAR-style insight string from descriptors.

    Procedure name: templated-sar-insight-stub

    In production, replace with an LLM call:
        sar_insight_llm(d) -> calls claude-opus-4-6 with a medchem prompt
    The register remains 'synthetic-acknowledged' in both cases.
    """
    permeation = "likely cell-permeable" if d.logp < 5 and d.tpsa < 90 else "permeation uncertain"
    drug_like = "within Lipinski-friendly range" if d.molecular_weight <= 500 else "above typical drug-like MW"
    return (
        f"Compound {d.compound_id}: LogP={d.logp} and TPSA={d.tpsa} — "
        f"{permeation}; molecular weight {d.molecular_weight} places it "
        f"{drug_like}; donor/acceptor profile ({d.hbd_count}/{d.hba_count}) "
        f"is balanced for oral bioavailability."
    )

"""Tests for sakshi's chemoinformatics worked example.

This file is tangled from codev/examples/chem.org.

The test suite walks a four-stage chemoinformatics pipeline (SMILES →
descriptors → Lipinski violations → templated SAR insight) and asserts
the firewall behaviour at each step, including the two pedagogical

RDKit-dependent tests are skipped if RDKit is not installed; the

from pathlib import Path

import pytest

    FailureClass,

    check_manifest,
    load_manifest,

HERE = Path(__file__).parent
CHEM_DIR = HERE / "chem"

def test_01_chem_correct_loads():
    """The clean manifest parses cleanly and passes all firewall checks."""
    manifest = load_manifest(MANIFESTS_DIR / "01_chem_correct.manifest.yaml")
    assert manifest.step == "chem-smiles-to-sar-insight-v1"
    check_manifest(manifest)


def test_01_chem_correct_has_four_outputs_with_registers():
    """The clean manifest's three outputs carry the right registers."""
    manifest = load_manifest(MANIFESTS_DIR / "01_chem_correct.manifest.yaml")
    by_id = {o.id: o for o in manifest.outputs}
    assert by_id["descriptors.parquet"].register.value == "derived-from-measurement"

def test_chem_manifest_uses_no_chemistry_specific_schema_fields():
    """The chem manifest uses only generic sakshi schema fields.

    This test makes the substrate-portability claim concrete:
    everything in the chem manifest is built from sakshi's generic
    vocabulary (register, derivation, synthesis, mode). Nothing in
    sakshi's schema mentions chemistry. If the doctrine were
    domain-specific, this test would be impossible to write.
    """
    import yaml

    raw = yaml.safe_load(
        (MANIFESTS_DIR / "01_chem_correct.manifest.yaml").read_text()
    )
    # The only domain-specific strings are in `description` and
    # `derivation`/`synthesis` *values* — i.e., free-form text the
    # schema does not constrain. The *keys* are all generic.
    chem_specific_keys = {"smiles", "molecule", "compound", "rdkit", "lipinski"}

    def walk_keys(obj):
        if isinstance(obj, dict):
            for k, v in obj.items():
                yield k
                yield from walk_keys(v)
        elif isinstance(obj, list):
            for item in obj:
                yield from walk_keys(item)

    keys = set(walk_keys(raw))
    leaked = keys & chem_specific_keys
    assert not leaked, (
        f"Chemistry-specific keys leaked into the manifest structure: {leaked}. "
        f"sakshi's schema should not need chemistry-specific extensions."
    )

* What this sketch demonstrates (and what it does not)

Concretely, the chemoinformatics portability sketch demonstrates:

1. *Schema accommodates a new topology*. sakshi's schema is /designed/
   as a property of the shape of scientific data pipelines, not of
   any specific domain. The chem manifests parse and validate using
   only generic vocabulary (register, derivation, synthesis, mode).
   The test
   ~test_chem_manifest_uses_no_chemistry_specific_schema_fields~
   makes this structural claim falsifiable. This is a claim about
   the schema, not about chemistry: it does not establish that
   sakshi's discipline is /sufficient/ for chemoinformatics, only
   that it does not /obstruct/ the substrate.

2. *The synthetic-acknowledged register is the honest answer*. The
   "SAR insight" layer is a templated string in this example and
   would be an LLM call in production. The register is identical
   either way. The discipline does not depend on whether the
   generator is statistical, deterministic, or neural — it depends
   on whether the manifest names the synthesis procedure honestly.

3. *Two real LLM-induced sins, caught at parse-time*. The two broken
   manifests catch the two most common errors when an LLM helps an
   engineer write a manifest:
   - Labelling the register correctly but forgetting the
     ~derivation~ field (the engineer or model knows the output is
     derived but doesn't name how).
   - Labelling the register correctly but forgetting the
     ~synthesis~ field (the engineer or model knows the output is
     generative but doesn't name how).
   Both are B-class — they fail at parse, before any pipeline runs.

4. *Optional dependency discipline*. RDKit is an optional dependency
   (install via ~pip install sakshi[chem]~). The manifest-level
   tests run without it; the pipeline-execution tests skip cleanly.
   This is the pattern for domain-specific worked examples that
   shouldn't bloat the core install.
